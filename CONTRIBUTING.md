# CONTRIBUTING.md

## Ground rules

1. **Implemented behavior only.** Docs, errors, and tests describe what the
   code does today. No "coming soon" features, no aspirational flags.
2. **Fail closed.** Any new input path must reject unknown versions, unknown
   algorithms, unknown enum variants, and unknown fields. Never guess.
3. **No new dependencies** without a written justification in the PR (V0.1
   has none beyond `serde_json`, crypto primitives, and `thiserror`).
4. **Determinism.** Same inputs must produce byte-identical outputs. If your
   change alters any artifact byte (including `demo/out/`), explain why in
   the PR and regenerate fixtures with the self-checking generators.
5. **Every failure has a stable code** from `proof-core::ErrorCode`. Do not
   invent ad-hoc strings.

## Development loop

```console
cargo build --locked
cargo test --locked           # full workspace suite
cargo fmt && cargo fmt --check
cargo clippy --locked --workspace --all-targets   # zero warnings
make demo                     # must stay deterministic; see demo/out/
```

Golden vectors live in `fixtures/` and are generated by the `gen_*_vectors`
examples, which assert their own output before writing. If a semantic change
is intentional, update the generator, rerun it, and say so in the PR — the
golden tests pin exact triples, so they will fail otherwise.

Toolchain: `rust-toolchain.toml` tracks stable (minimal profile); CI and the
release provenance both record the exact tested version (1.98.1 at last
cut). MSRV is not established — do not add `rust-version` to any manifest
until an older toolchain has actually run the full gate. Coverage:
`cargo llvm-cov --locked --workspace --summary-only` (needs
`cargo install cargo-llvm-cov`; ~80% lines at last cut, envelope modules at
~100%). Fuzz seed corpora replay on stable (`*/tests/fuzz_seeds.rs`); the
libFuzzer smokes stay nightly-only (see `fuzz/README.md`).

## Adding code

- Keep trust logic in `proof-verify` / `proof-policy`; the CLI adds no trust
  logic of its own and re-verifies every artifact it loads.
- New pipeline behavior belongs to a numbered stage with a check record; new
  policy behavior to a closed `Requirement` variant with evaluation + tests.
- Tests: unit tests next to the code; integration tests under `crates/*/tests/`;
  hostile-path cases (malformed, oversized, tampered, unauthorized) must keep
  failing with documented codes — add one for each new path.

## Commits and PRs

- Small, single-purpose commits; imperative subject lines
  (`pipeline: reject future issued_at`).
- The PR description states what changed, which tests cover it, and whether
  any fixture/doc/behavior changed. CI must be green: build, tests, fmt,
  clippy, demo determinism.

## Reporting bugs

See `SECURITY.md` for vulnerability reporting. For regular bugs, open an
issue with the exact command, input files (or generator), expected verdict,
and actual verdict — the engine is deterministic, so a repro is always a
byte-exact artifact.
